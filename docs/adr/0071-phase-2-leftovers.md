# 71. Phase 2's leftovers: narrow headers, Add Tags, big imports and exports

- Status: Accepted
- Date: 2026-11-03
- Refers to: SPEC §4.1, §4.6; `docs/briefs/phase-3a.md` (slice 7); `docs/briefs/phase-2-report.md` ("Known limits from the PRs"); ADR 0058 (toasts and breakpoints at 360 px), ADR 0064 (small polish), ADR 0065 (shared selection mode), ADR 0068 (archive), ADR 0070 (practice)

## Context

Phase 2 listed what it left: All Cards' filters cut in French, headers cut at 360 px when minimise and maximise are shown, Add Tags turning text into a pill when the window shrinks, a 256 MiB file refused only after 21 s on a worker with no Cancel, and exports above 2 GiB of media that cannot be imported again. This ADR records the decisions that fixed them, one section per item.

## 1. Filters and headers at 360 px

**Filters.** The three (four, with archived decks) drop-downs of All Cards are in an `AdwWrapBox` (libadwaita 1.7, the version Cargo.lock builds against has it; `justify: fill` with `justify-last-line`): each is as wide as its text, and a line breaks where they do not fit side by side. French at 360 px takes three lines ("Tous les paquets" / "Toutes les étiquettes" and "Tous les états" / "Archivés masqués"), English two. Nothing is cut except a single entry wider than the line (a long deck name), which `ui::dropdown::shrinkable` still ends in "…" and whose tests stay. Two equal columns or a popover were rejected: the first still cuts "Toutes les étiquettes", the second hides the filters behind a tap. The `FilterLayout` of ADR 0068 is removed.

**Deck page.** Select Cards leaves the header under 400 sp for the bottom bar, next to Study (its slot, a `GtkBox`, is what the breakpoint hides: selection mode shows and hides the button itself, so a setter on the button would be overwritten). `ui::selection::Parts::narrow_select_button` takes the keyboard when selection mode ends and the header's button is not showing. The subtitle keeps one count on a phone, the due cards or, with none, the new ones (`study_subtitle(input, compact)`), the full line being the title's tooltip.

**Selection header.** Under a 400 px window it shows the bare count ("30") as its title, the full "30 sélectionnées" as a tooltip (`selection_title_tight`). It follows the window's width through `ui::breakpoint::follow_window_width` (the surface's `layout` signal), not a breakpoint: the page already has two, and `AdwBreakpointBin` applies only the last matching one, so a third would repeat their setters; and an `AdwBin` has a layout manager, so its `size_allocate` is never called.

**Review page.** Under 400 px Edit Card leaves the header for the Card Menu (which has "Edit Card" at all widths now), so the title and the subtitle ("30 restantes") fit beside Back, Undo, the menu and the window buttons (`edit_button_shown`).

## 2. Add Tags when the window shrinks

Shrinking the window (an on-screen keyboard) with Add Tags open turned the typed name into a pill (#95). Cause, found in the harness (`scripts/screenshot.py`, `resize:360,330`): at that height libadwaita's `AdwFloatingSheet` takes the keyboard focus for its own `sheet` widget, so the field sees its focus leave, and the idle that decides (ADR 0051) found the focus "elsewhere in an active window" and split. The focus was on a container around the field, which nobody chose.

`keys::after_leave(active, inside, ancestor)` now returns `Nothing`, `Split` or `Refocus`: a focus that fell back to an **ancestor** of the field gives the focus back to the text (cursor kept, nothing selected: `GtkText` would select everything) and makes no pill. A focus that went to another widget (Tab, a click on a button or another field) still makes the pill, as before, in the card editor too. Consequence: a click on the blank background of a dialog around the field keeps the name typed and the focus in the field instead of making a pill; pressing Add or Save still counts it. Test: `shrinking_the_window_keeps_what_is_typed_in_add_tags` (a real dialog, a real resize); it fails when `Refocus` is made `Split`.

## 3. An over-large import is refused early, and its plan can be cancelled

**What took 21 s.** A file over the archive limit (2 GiB) was already refused from its size alone, before any read (`Archive::walk`, and a test with a sparse file). A `cards.json` over its limit (256 MiB) was not: only a media entry's declared size was checked in the central directory, so `cards.json` was read, hashed and inflated up to the cap before `EntryTooLarge`. `Archive::open` now refuses a `cards.json` that declares more than `Limits::json` the same way (same error, same message), after the checks of the layout, so nothing of it is read. One test expectation changed: a zip64 uncompressed size of 2^64 − 1 is now `EntryTooLarge` instead of `InvalidArchive` (`zip64_fields_at_the_extremes_are_refused`); it is refused either way, and earlier. A size that lies is still caught while reading, which is capped at the same limit, so both checks stay. The entry count and the central directory's size were already checked from the end record. `MAX_ARCHIVE_BYTES` (2 GiB) is now one public constant, which `Limits::DEFAULT` and the export (section 4) share.

**The Anki path** (ADR 0061) has the same archive checks (`AnkiLimits::archive` is a `Limits`). Its collection and media list are checked against their limits from the declared sizes too, but only in the legacy formats: in the current one the entry holds zstd's *input*, the limit caps its *output*, and a frame can be padded with skippable frames, so a large declared size proves nothing. There the cap while reading stays the only check.

**Cancel.** `Store::plan_import_cancellable(path, &AtomicBool)` wraps the file's reader in `source::Cancellable`, which fails at its next read once the flag is set; whatever the failure became (a refusal, an IO error), a flag that is set makes the result `Error::ImportCancelled`. Reads go through 64 KiB buffers, so it stops within moments. A plan never writes, so nothing needs undoing; a test cancels it before the first read and at each of the eleven reads of a step-by-step plan, and counts that no read begins after the cancel. `plan_import` keeps its signature. In the app, `AppState::plan_import_on_worker` takes the flag and the dialog shows the Anki import's toast, "Checking the file…" with **Cancel**, now `transfer::progress::Progress`, which also makes **Escape** cancel from anywhere in the window (the toast takes no focus; its button is reachable by Tab, but Escape needs no search for it): the controller is in the capture phase of the window and is removed when the job ends. A cancelled plan says "Import cancelled", as the Anki import does. The apply is not cancellable (it is one short transaction after the plan; the Anki import's is a long conversion).

**Tests.** `a_cards_json_declaring_more_than_the_limit_is_refused_unread` (a valid small file whose central record lies, so only the declared size can give this error; CPU-bounded as ADR 0049, the limit itself accepted), `a_plan_is_cancelled_at_any_read_and_writes_nothing`, `a_collection_declaring_more_than_the_limit_is_refused_unread` (Anki, legacy), `escape_cancels_in_the_capture_phase_and_the_button_cancels_too`.

## 4. An export that could not be imported again says so first

**The problem** (ADR 0054, consequences): an import reads at most 2 GiB from a file (ADR 0053), and an export holds every media file, so a collection with more than 2 GiB of media exported a file that Rappel itself then refused. Exports are how people back up.

**Decision.** *No format change.* Before the file chooser and before anything is written, Export… adds up the media (`Store::media_totals`: one `SUM` and `COUNT` over the `media` table's `bytes`, on the main thread) and asks the pure `media_too_large_for_import(MediaTotals)`. It adds, to the media's sizes, what their zip entries take besides data (226 bytes each: two headers and two 75-byte names) and the archive's fixed 206 bytes, and compares with `MAX_ARCHIVE_BYTES` (the constant the import's `Limits::DEFAULT` uses): exactly at the boundary (the archive may be the limit and no more). `cards.json` is not counted, so a `false` is not a promise and a `true` is always right. The alert **"Export Without Media?"** says what the media come to ("3.0 GiB"), that an export with them could not be imported again by Rappel, and what the other choice keeps; its responses are **Cancel** (the default and the close response: Enter and Escape never export) and **Export Without Media**. Cancel returns to the window with nothing chosen or written; Export Without Media goes on to the file chooser and writes the normal format version 2 with no `media/<sha256>.<ext>` entry and no media record (`ExportOptions { include_media: false }`; `ExportSummary::media_left_out` counts the rows). The toast stays, "Media left out. Exported to “…” without its N media files".

**The importer takes it already.** Cards keep their `media:` references to files that are not in the file (SPEC §4.1: a card may name a media file that is in neither the file nor the database); the plan counts no media, and importing into a database that has the files adds nothing and conflicts with nothing. Tests: it imports into an empty database, round-trips (export again without media: the same bytes), is deterministic, equals the full export but for `media`, and the full export has nothing else changed.

**The guard for what the estimate cannot know.** The text of a very large collection could still push a file just under the line past it. `export_to_with` checks the size of the file it wrote before renaming it; past `MAX_ARCHIVE_BYTES` it is `Error::ExportTooLarge`, nothing replaces the file at the path, and the toast says "The export failed: the export is N bytes, more than the 2147483648 bytes an import reads; export without the media instead" (the second try is then the question's answer). Tested with a lowered limit.

**Not done:** a backup that is not an export (the database copy `Restore Backup` uses) is untouched; nothing splits an export over several files.
