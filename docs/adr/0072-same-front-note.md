# 72. A note when another card has the same front

- Status: Accepted
- Date: 2026-11-03
- Refers to: SPEC §4.4; issue #119; `docs/briefs/phase-3a.md`; ADR 0033 (Card Information), ADR 0035 (the search index), ADR 0050 (hostile queries), ADR 0059 (translation), ADR 0068 (archived decks)

## Context

People add the same card twice without noticing, often months apart or in another deck. Issue #119 asks the card editor to say so while a card is written or edited: a quiet note under the Front field, "A card in “Spanish” has the same front", with a way to open that card, and never a block on saving, since two cards may share a front on purpose (the same word with two meanings, or in two decks). Fronts are compared by their plain text, ignoring case, accents and surrounding or repeated whitespace; exact match only. Every live card counts, archived decks included (and the note says so); the card being edited and deleted cards do not. The lookup is debounced, one indexed query, fast at 10,000+ cards, and the note's text comes from a tested pure function. It must be announced politely to screen readers, and its link reachable by keyboard. No migration, no export change, no new setting.

## Decision

**What "the same front" is.** `storage::front_key(front_md)`: the search index's text of the front (`content::search_text`, ADR 0035: the plain text the user reads, Markdown syntax left out, math and code as their source, an image as its alt text, links as their words, in lower case with accents removed by Unicode decomposition), then every run of whitespace (newlines included) as one space and none at the ends. Two fronts are the same when their keys are equal. So "**El Niño**", "el nino" and " EL\n\nNIÑO " are the same; "Hola!" and "Hola" are not, since punctuation is text the user reads, and "$x^2$" is the same as "x^2", as search already treats them. Letters that do not decompose (ß, ø, ł) stay as they are, as in search.

**The query, without a migration.** `cards_fts` already holds every card's folded front (written with every card write). `Store::cards_with_front(front_md, except_id)` sends one FTS5 query, `front : ^ "<key>"`: a phrase restricted to the `front` column and anchored to its first token (`^`), the key's quotes doubled, so nothing typed is ever FTS5 syntax (`NEAR`, `*`, `-`, `:`, parentheses and `"` are all just text; tested). The phrase starts at the key's first token character, so leading punctuation ("¿gato") does not stop the anchor matching. It finds every front that starts with the key's words in order; joined to live cards in live decks (archived ones included) other than the edited card, each row's stored front is then compared with the key word by word in Rust, so a front that only starts with the words ("gato negro" for "gato") is dropped. The results come with the deck's name and whether it is archived, decks not archived first, then the newest card first.

A token character is a letter or digit (Rust's `is_alphanumeric`, which covers unicode61's default token categories `L*` and `N*`) or a private-use character (`Co`: U+E000–U+F8FF and the two supplementary planes), which unicode61 also reads as part of a token and Rust does not call alphanumeric. Without it, a front starting with one joined to a word ("\u{E000}abc", one token) was looked up as "abc" and missed. All Cards' search (`fts_query`) has the same miss for a word starting with a private-use character; it is left to the next clean-up.

- **Bounded work.** FTS5 reads each token of a phrase (ADR 0050), so only the key's first 256 bytes from its first token character go into the phrase; a cut key ends in `*`, so a word cut in two still matches, and the full comparison in Rust decides. Parsing and folding the front is what costs: 1 MiB of dense Markdown took 87 ms in a release build and 330 ms in a debug one, on the editor's main thread at every pause in typing (the preview parses at most 32 KiB). So a front longer than 64 KiB (`MAX_SAME_FRONT_BYTES`) is not looked up at all and has no note: such a card is not typed twice by mistake. At 64 KiB, the lookup takes 20 to 34 ms in a debug build; a word every one of 10,000 fronts starts with, 26 ms. `tests/perf.rs` bounds them at 400 ms and 250 ms.
- **A front without a token character** ("?", "+ - *", "$+$"), or only symbols FTS5 does not index, such as ⓐ (Rust calls it alphanumeric; unicode61 reads it as a separator), gets no note: it has no token for the index to look up, and comparing it with every card would be the unbounded scan the index exists to avoid. Such fronts are rare and short, and a missed note costs nothing. A NUL typed in the editor (a card can never hold one) only makes the front differ from every card.
- **Rejected:** a stored, normalised front column with its own index (a migration, which the issue rules out); a plain `LIKE` on `cards.front_md` (Markdown, case and accents would count, and it scans every card).

**What the property test checks.** Fronts and the typed text are drawn from a tiny alphabet (a, A, é, É, U+E000, space, newline, tab, "!"), and the typed text is usually one of the fronts changed in ways that keep its key (upper case, accents decomposed to NFD, whitespace added around and inside, wrapped in `**…**`), else unrelated text from the alphabet. Over 256 cases, the cards found must equal those whose key, computed by an oracle in the test from the definition above (not by calling `front_key`), equals the typed text's (none when it has no token character), newest first; and at least half the cases must have a match, so a bug that only misses matches cannot pass. Checked by mutation: a key without collapsed whitespace, a stored front compared without collapsing it, and a phrase starting at the first `is_alphanumeric` character each fail it.

**The note.** A pure function, `dialogs::card_editor::same_front::note`, decides the text from the cards found:
- one card: "A card in “Spanish” has the same front", or "A card in the archived deck “Spanish” has the same front";
- several in one deck: "2 cards in “Spanish” have the same front" (or "in the archived deck “Spanish”");
- several decks: "3 cards in several decks have the same front", with ", archived decks included" when any of them is archived.

Each is one whole translated sentence with named placeholders and a plural (ADR 0059), translated into French. The label shows it without markup (`use-markup: false`): it holds a deck's name, which is the user's text, so nothing in it is ever read as Pango markup (tested with a deck named `a&b <i>`). It is a dimmed caption under the front's frame (`dimmed`, `caption`: the HIG's secondary text, no colour of its own), above the side's length error when both show.

**When it is looked up.** 400 ms after typing in the front pauses (`ui::debounce`, like the preview's 250 ms; a little longer so the note does not flicker while a word is half typed), and at once when a card is loaded: editing a card, and the empty next card after Ctrl+Shift+Enter, which starts without a note. Typing in the back or the tags does not look up again, nor does a front unchanged since the last lookup. The query runs on the main thread, as All Cards' search does: it is one indexed query of a few milliseconds (at most tens in a debug build, thanks to the 64 KiB cap), off the keystroke path since it waits for the pause; only the front's text is read from the editor. A failed lookup only hides the note (logged at warn); it is a hint, never an error toast.

**Show Card.** Beside the note, a flat button opens the first card found in Card Information (ADR 0033), as a dialog over the editor. Rejected: a second editor over the first (two unsaved texts and two Save buttons at once), and switching the editor to that card after the discard question (the editor belongs to its deck's page, which updates its list from what it saves; the other card may be in another deck or an archived one, and the user would lose the place of the card being written). Card Information is read-only, shows the card's front, tags, dates and history, and leaves what was typed untouched; when it closes, the focus goes back to Show Card. With several cards, the first is the one in a deck not archived, newest first; All Cards remains the place to see them all.

**Accessibility.** When the note appears or its text changes, it is announced with `gtk_accessible_announce` at `GTK_ACCESSIBLE_ANNOUNCEMENT_PRIORITY_MEDIUM` (GTK 4.14; the polite level), from the front's text view, as the length errors are; not on every key, since the lookup waits for the pause and an unchanged note is not announced again. The front's text view is described by the note (`described-by`, beside the length error), and Show Card is described by it too, so its short label is read with its context. Tab from the front reaches Show Card (the text views do not take Tab). If the note goes while Show Card has the focus, the focus goes back to the front instead of being lost. A hidden note's label is emptied, so the front's description never reads an old note.

## Consequences

- No schema, export or setting changed: the note reads the search index every card write already keeps.
- The note counts deleted cards out and archived decks in; a deck that is deleted takes its cards out of the note with it.
- What counts as "the same" is the search index's folding plus whitespace; if that folding changes, the note follows it.
- Fronts made only of punctuation or symbols never get a note, nor do fronts over 64 KiB.
- Opening a card from the note shows its information, not its text for editing; to change that card, the user goes to it after closing the editor.
